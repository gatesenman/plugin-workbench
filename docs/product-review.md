# 产品诊断与路线图 · 通用 AI 辅助插件开发工作台

> 评审日期：2026-10-14 · 更新：2026-10-19（P1 优化轮） · 评审方式：通读 `src/core/*`、`src/server/server.js`、`ui/*`，在 xvfb 下驱动 Electron 应用（mock 提供方）走完各流程，并查看 `screenshots/`。

## 1. 定位

**「通用 AI 辅助插件开发工作台」**：给出一句需求，不管目标宿主是 VS Code、Blender、飞书，还是公司内部系统，都能拿到一个**可构建、可校验、可打包**的插件项目，后续继续用 AI 迭代，直到发布。

定位的三个关键词和对应的产品承诺：

| 关键词 | 承诺 | 评审前的状态 |
|---|---|---|
| 通用（ANY vendor） | 715 个宿主 / 23 个适配器家族；不在目录里的宿主也能接入 | ✅ 目录覆盖广；⚠ 「AI 扩展新厂商」藏在目录页底部，和创建流程是分开的 |
| AI 辅助 | AI 是主路径：理解意图 → 方案 → 生成 → 修复 → 迭代 | ❌ AI 只是各个面板里的附属按钮，主路径还是「先选厂商 → 选模板 → 手动跑流水线」 |
| 工作台 | 一个地方完成全生命周期，状态可追溯 | ✅ 流水线完整；❌ AI 写盘之后没法撤销，没有项目历史，也没有首页 |

## 2. 目标用户（Personas）

1. **跨宿主的独立开发者「阿杰」**：熟悉 JS/Python，但每个宿主的清单格式、打包方式、调试方法都要现查。核心诉求是不查文档也能先跑起来，然后快速迭代。
2. **企业内部工具开发者「王工」**：要给公司自研 CAD/MES/OA 系统，或者冷门的行业软件写插件，目录里大多没有这些宿主。核心诉求是未知宿主也能被结构化接入，团队之间能复用。
3. **懂业务的半技术人员「产品经理 / 设计师」**：会描述需求，但不熟悉工程细节。核心诉求是只用自然语言就能做出能装上的插件，并且看得懂 AI 在做什么、能撤回。
4. **插件平台/生态运营方（次要）**：想降低自家平台的插件开发门槛。核心诉求是能把自家平台的规则和文档注入工具。

## 3. 核心 Jobs-to-be-Done

- J1：*当我有一个插件想法时*，我想用一句话描述，然后直接拿到能在宿主里加载的项目。
- J2：*当目标软件不在列表里时*，我希望工具自己推断技术栈和清单格式，而不是让我去填适配器 JSON。
- J3：*当构建失败时*，我希望 AI 自己定位并修好，我只需要看结论；修错了也能撤回。
- J4：*当我要改功能时*，我想用对话描述改动，AI 改代码之后自动验证。
- J5：*当我准备发布时*，我想知道在宿主里怎么运行、调试和上架，并拿到符合规范的产物。

## 4. 现状差距（评审前，基于实际代码）

| # | 差距 | 证据 | 影响 |
|---|---|---|---|
| G1 | **入口不是 AI**：启动后默认是内嵌 IDE 页加资源管理器，新建项目要在对话框里手输厂商 id | `ui/index.html` 默认 tab 为 `ide`；`#dlg-new` 的厂商字段是 datalist | 违背定位，新用户第一步就卡住 |
| G2 | **无意图识别**：没有任何代码把「Chrome 扩展」「飞书机器人」这类描述映射到宿主 | `server.js` 没有相关 API | J1 无法完成 |
| G3 | **未知宿主扩展和创建是割裂的** | `aiExtendVendor` 只能在目录页单独调用 | J2 要多走 4 步 |
| G4 | **没有方案（spec）步骤**：AI 直接改文件，用户无法事先修正 AI 对需求的理解 | `aiDev` 直接返回文件 | 返工成本高，用户也难建立信任 |
| G5 | **没有 Agent 闭环**：构建失败要手动点「AI 调试 → 应用修复 → 再构建」 | `ui/app.js runStage` | J3 体验差 |
| G6 | **没有宿主知识注入**：AI 提示词里只有清单文件名，不包含规则和文档；用户也看不到运行/调试方法 | `ai.DEV_SYSTEM` | 真实 LLM 生成的代码不合规，用户不会在宿主里运行 |
| G7 | **AI 改动不可撤销**：`applyFiles` 直接覆盖文件 | `lifecycle.applyFiles` | 半技术用户不敢用 |
| G8 | 无首页、无最近项目、无引导 | — | 冷启动体验差 |
| G9 | Mock 生成的代码基本是骨架（`aiFeature(){ TODO }`），离线演示不了「真实功能」 | `ai.enhanceFromRequirement` | 离线演示的价值有限（需要接真实模型） |
| G10 | 构建是语法级的（`node --check` / `ast.parse` / JSON 解析），不调用宿主的官方工具链（vsce、web-ext、blender 等） | `lifecycle.build` | 「构建通过」≠「宿主可加载」 |
| G11 | 发布只有 dry-run，没有凭据管理；版本、变更日志很简单 | `publish` | 不影响 MVP，但离发布闭环还有距离 |

## 5. 路线图

### P0 —— 把 AI 变成主路径（本次已实现 ✅）
1. ✅ **AI-first 首页**：「描述你想做的插件」输入框、6 条示例、5 步进度条、最近项目、上手指南（可关闭）。
2. ✅ **意图 → 宿主匹配**：名称/别名打分，未知宿主（引号点名但不在目录中，或完全匹配不到）给出适配器提案；接入真实 LLM 时先让 LLM 抽取宿主名再匹配。支持手动改选。
3. ✅ **未知宿主自动扩展**：确认方案执行时自动 `addCustom` 写入目录，不用再去目录页。
4. ✅ **可编辑方案（Plan/Spec）**：项目名、概述、功能点、验收标准、自动修复上限都可以改；同时生成 `SPEC.md` 并写入项目元数据。
5. ✅ **Agent 循环（可见步骤）**：准备适配器 → 脚手架 → AI 生成 → 构建 →（失败）AI 诊断+修复 → 重建 … 最多 N 次 → 清单校验+AI 审查；后台任务加前端轮询，实时显示步骤和日志。
6. ✅ **宿主知识库**：14 个家族的清单规则、官方文档链接、运行/预览、调试指南；注入 DEV/DEBUG/PLAN 提示词，并在方案页和结果页展示。
7. ✅ **检查点与撤销**：每次 AI 写盘（生成、迭代、自动修复、一键修复、聊天动作）之前自动快照；撤销前也会先保存当前状态；生命周期页可以浏览和恢复任一检查点。
8. ✅ **对话迭代**：结果页的迭代框，以及聊天新动作 `agent_iterate`（描述改动 → 生成 → 构建 → 自动修复）。
9. ✅ 一键「打包 + dry-run 发布」。

### P1 —— 让「通过」更可信
- ✅ **宿主官方工具链适配（best-effort）**：`vsce` / `npx @vscode/vsce package`、`web-ext lint`、`office-addin-manifest validate`、`blender --command extension validate`。检测到 PATH 上有工具时调用；缺失时步骤日志写明「未检测到官方工具，已跳过」，**不阻断**产品流程。
- ✅ **Agent 逐步确认模式**：设置「自动应用 AI 改动」（默认开）。关闭后 Agent 在写盘前暂停，展示文件级 diff，可批准/拒绝；仍保留检查点撤销。
- ✅ **SSE 流式步骤 + 取消**：`GET /api/agent/jobs/:id/events`；执行卡片提供「取消」按钮，可在循环中安全中止。
- ✅ **更完整的离线 Mock**：VS Code / Chrome / Blender / Office 生成可演示的命令、popup、面板、taskpane（不再是 TODO 骨架）。
- ✅ **聊天 UX**：状态类刷屏折叠进紧凑活动时间线；保留 ACTION 按钮。
- ✅ **代码页**：隐藏 Get Started；编辑器主题随应用浅/深色同步；加载占位 + 重试。
- ✅ **项目抛光**：首项目上手清单、空状态、版本 **1.1.0**。
- ⏳ 检查点之间的完整 diff 视图；撤销粒度细化到单个文件（仍可整快照恢复）。
- ⏳ 知识库扩展到厂商级细节；用户粘贴文档 URL/片段作为项目上下文。
- ⏳ Authenticode / 商店真实发布凭据（仍为 P2）。

### P2 —— 生态与团队

## 6. 诚实说明
- 离线 Mock 下，「AI 生成」是模板加关键词骨架，「AI 修复」是规则修复：语法错误时会用一个最小可运行的入口替换整个出错文件。这个流程本身是真实可用的（构建、校验、检查点都会真实执行），但代码质量要靠接入真实模型。
- 意图匹配在 Mock 下是确定性的名称/别名打分。描述里同时出现多个宿主名时，选最长匹配，其余作为候选列出。
- 「构建通过」仍以语法级 + 清单字段校验为主；若本机装有官方工具链会额外跑一遍（见 P1 ✅），缺失则跳过并记入日志（G10 部分缓解）。
